JUnit XML formatn't

Olivia Published on 2026-09-03 at 20:23:53+02:00 License: CC-by-SA 4.0 (text), MIT (code)
junit java

While masochistically deciding to write my own TUI wrapper for various specific test frameworks that I can control, I noticed the JUnit reporter. According to a few places on the interwebs, like this random github repo with 147 stars and what appears to be multiple AI slop written regurgitations of it, JUnit's XML format is a defacto standard.

While JUnit still seems to generate this format by default, they have an alternate test reporter that uses a different XML-based format, open test reporting. At the time of writing, it's maintained by the JUnit devs.

I stumbled into this while looking at this bug reported in 2022 while looking for basically the same bug regarding @ParameterizedTest. With @ParameterizedTest, the JUnit format is generated by default with incredibly unhelpful test names:

  <testcase name="[1] 1" classname="test.TestTest" time="0.001"/>
  <testcase name="[2] 3" classname="test.TestTest" time="0.0"/>
  <testcase name="[3] 5" classname="test.TestTest" time="0.0"/>
  <testcase name="[4] -3" classname="test.TestTest" time="0.0"/>
  <testcase name="[5] 15" classname="test.TestTest" time="0.001"/>
  <testcase name="[6] 2147483647" classname="test.TestTest" time="0.001"/>

Whereas the new one is much more useful:

  <!-- The class is a container -->
  <e:started id="4" name="TestTest" parentId="1" time="2026-09-03T18:30:18.964133639Z">
    <metadata>
      <junit:uniqueId>[engine:junit-jupiter]/[class:test.TestTest]</junit:uniqueId>
      <junit:legacyReportingName>test.TestTest</junit:legacyReportingName>
      <junit:type>CONTAINER</junit:type>
    </metadata>
    <sources>
      <java:classSource className="test.TestTest"/>
    </sources>
  </e:started>
  <!-- The test itself is considered a container as well -->
  <e:started id="10" name="testName(int)" parentId="4" time="2026-09-03T18:30:19.005424922Z">
    <metadata>
      <junit:uniqueId>[engine:junit-jupiter]/[class:test.TestTest]/[test-template:testName(int)]</junit:uniqueId>
      <junit:legacyReportingName>testName(int)</junit:legacyReportingName>
      <junit:type>CONTAINER</junit:type>
    </metadata>
    <sources>
      <java:methodSource className="test.TestTest" methodName="testName" methodParameterTypes="int"/>
    </sources>
  </e:started>
  <!-- Then the actual test runs begin -->
  <e:started id="11" name="[1] 1" parentId="10" time="2026-09-03T18:30:19.010532913Z">
    <metadata>
      <junit:uniqueId>[engine:junit-jupiter]/[class:test.TestTest]/[test-template:testName(int)]/[test-template-invocation:#1]</junit:uniqueId>
      <junit:legacyReportingName>testName(int)[1]</junit:legacyReportingName>
      <junit:type>TEST</junit:type>
    </metadata>
    <sources>
      <java:methodSource className="test.TestTest" methodName="testName" methodParameterTypes="int"/>
    </sources>
  </e:started>
  <e:finished id="11" time="2026-09-03T18:30:19.012924917Z">
    <result status="SUCCESSFUL"/>
  </e:finished>
  <e:started id="12" name="[2] 3" parentId="10" time="2026-09-03T18:30:19.013730812Z">
    <metadata>
      <junit:uniqueId>[engine:junit-jupiter]/[class:test.TestTest]/[test-template:testName(int)]/[test-template-invocation:#2]</junit:uniqueId>
      <junit:legacyReportingName>testName(int)[2]</junit:legacyReportingName>
      <junit:type>TEST</junit:type>
    </metadata>
    <sources>
      <java:methodSource className="test.TestTest" methodName="testName" methodParameterTypes="int"/>
    </sources>
  </e:started>
  <!-- Truncated, there's the same number as the last run, but obviously a lot more lines -->

The format itself is somewhat heavily parsed still, but that's a manageable problem. The format I can only find being called the "JUnit [XML] format" or "the format used by JUnit", on the other hand, just annihilates the test name context.

I briefly considered making a JUnit XML parser just because Catch2 is able to generate it, and it is widely accessible in general, but looking at this did mildly turn me away from that idea. Catch2, for example, introduces its own flavour of hierarchy in the JUnit test reporter, by using / within the name to denote TEST_CASE/SECTION trees. As demonstrated with the JUnit case, it (in theory) appends the data to the name, if the way whatever the fuck wasn't set up to annihilate the name by default unless you hard-code a name in the annotation to override it.

The new standard does look more promising in that regard, but it isn't implemented in Catch2, which is what I was supposed to be working on before I briefly wondered if there was a light at the end of the tunnel for avoiding reading gradle's shitty fucking output when executing Java/Kotlin tests, but that'll have to wait another few procrastination cycles.

JUnit's XML is dead, long live JUnit's new XML?
